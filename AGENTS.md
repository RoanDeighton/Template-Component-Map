# Working in this codebase

This is the durable technical reference for the crawler/analyzer pipeline and the content-authoring workflow built on top of it. For copy style rules, see [CLAUDE.md](CLAUDE.md). For the current project state and chronological history, see [HANDOFF.md](HANDOFF.md).

## The core principle: this tool must stay site-agnostic

Everything in `src/` (the crawler and analyzer) has to work on any site's markup, not just whichever site was tested most recently. When a bug or quality issue turns up, fix the general algorithm, never patch for one site's specific classes, attribute names, or content shape. Before shipping a fix, ask: would this also help a completely different site with different markup? If not, it's the wrong fix. This came up repeatedly building out a second real dataset (Revolut) after the first (Rijksmuseum) — every fix below was written to that standard.

## `src/crawl.ts` + `src/lib/navDiscovery.ts` — discovery

Default discovery is nav/footer-first, not a brute-force crawl: follow the header/nav and footer links from the start URL, then check each of those pages for a large repeating section (a listing) and sample a few pages from it instead of visiting every one. This keeps crawl cost roughly constant regardless of site size. The legacy full sitemap + link-crawl approach (`--legacy-discovery`) still exists as a fallback, offered as "expand search" at the review checkpoint if nav-based discovery looks too thin.

When merging listing samples found on different nav/footer pages, always merge by pattern *before* sampling, not per source page — the same listing (e.g. `/legal/*`) is often linked from many different pages, and sampling per-page instead of per-pattern causes duplicate/inflated capture lists.

## `src/analyze.ts` — clustering

This is the part most likely to need tuning per site, and where most of the subtlety lives.

**Two different fingerprints, two different jobs** (`contentFingerprint()` vs `templateFingerprint()`):
- `contentFingerprint()` (coarse) decides component *identity* — is this the same reusable widget, regardless of content? Deliberately loose: no DOM tag (a `<section>` and a `<span>` wrapping the same widget still match), and heading/element counts bucketed into just a few wide tiers (none/one/many; compact/large) so a 5-question FAQ and a 15-question FAQ, or a short legal document and a long one, still count as one component. Tag is kept for header/footer specifically, since "what tag renders the header" is a real structural fact there, not incidental styling.
- `templateFingerprint()` (fine) decides page/template *similarity* — pages should stay distinct even when they share one similar-looking section. Keeps the tag and the original fine-grained buckets. **Do not let template clustering and component identity share one fingerprint** — they were briefly merged and it caused pages to over-cluster into "the same template" whenever a shared coarse-matched widget happened to appear on both, which is a different failure mode than the one the coarse fingerprint was built to fix.

**`buildOutline()`'s wrapper-peeling**: some CSS-in-JS design systems nest a page's real sections inside a layout-only wrapper div with no content of its own (positioning/max-width wrappers). Walking only *direct* children of `<main>` then collapses an entire page's real sections into one outline entry. `peelWrapper()` sees through this by DOM shape alone (an element with no text of its own and exactly one child, whose own child in turn has multiple children) — never by class name, so it works regardless of a site's naming conventions.

**Stable-ID detection** (`detectStableIdAttr()` / the merge pass in `reconcileComponents()`): some sites mark up "this is the same content block" with their own attribute (found `data-blockid` on Revolut, a CMS block-instance ID). Detected generically — scan `id` plus every `data-*` attribute across every page, and use whichever one (if any) has many distinct values with real cross-page reuse. Most sites have nothing that qualifies and this is a no-op.

**Critical constraint on stable IDs, learned the hard way**: only trust a UUID-shaped value as a literal per-instance identifier. A short, human-readable value (`"navigation"`, `"signup-button"`) is a *role* label a CMS applies to every instance of that role, including structurally different ones — it collapsed a legal page's genuinely different, link-free header into the main site header purely because both happened to carry `data-blockid="navigation"`. A stable ID must only ever confirm "these two are the exact same literal content instance." It must never become a substitute for structural fingerprint matching, and it must never cause a component used with different content on different pages to be treated as different components — that's still, and should always be, the fingerprint's job.

**Known remaining limitation**: fingerprint matching is a lossy hash of ~7 coarse signals. It can still occasionally merge two genuinely different widgets that happen to share every bucketed signal (an icon row using CSS/font icons instead of `<img>`/`<svg>` looked identical to a plain text intro, since neither registers as having an image). There's no full fix for this without a fundamentally richer signal (visual layout, DOM subtree shape hashing); when it happens, it's a content-authoring judgment call, not a bug to chase.

## Content authoring (`output/<site>/content/`)

- **Offer light vs. full mode up front** once a new site's crawl finishes: light = just enough structure to render (site overview, components table, asset symlink, no per-component descriptions); full = complete hand-authored pass matching Rijksmuseum's depth. This is a real time/effort tradeoff, not a default to assume either way.
- **Components must be authored before page/template docs.** Page docs link to components by name; writing pages first means writing broken links now and backfilling later.
- **`components/overview.md` is one flat markdown table**, functional and editorial components together, sorted however. The app does the functional/editorial split, sorting, and amount-hiding *at render time* — pre-splitting the source file into two separate tables breaks the parser (`getComponentsTable()` in `web/lib/content.ts` only reads the first table it finds) and produces duplicate section headings.
- **Generate cropped example images as part of the same step components are authored**, not as a follow-up pass. Each captured page has per-section bounding box data (`style.top/height/width` in `analysis.json`'s page outline) — crop the representative screenshot to just that box (plus ~12px padding) rather than showing the reader the entire page. Skipping this the first time on Revolut meant redoing all 87 components' example images afterward.
- **Slug collisions are real and likely** when authoring components in parallel batches — independent batches choosing titles without seeing each other's choices produced 4+ collisions on both the first and second Revolut passes (same slug, different underlying components, one silently overwrites the other). Always run a validation pass afterward: for every canonical component key, compute Jaccard similarity between its `usedOn` set and every written file's `usedOn` set; anything below ~0.9 similarity is a missing or wrongly-merged file, and multiple keys landing on the same file at ≥0.9 is a collision. Fix gaps directly rather than re-dispatching a whole new batch.
- **One automated QA pass at the end, not iterative discovery**: validate every file's YAML actually parses (a bare colon inside an unquoted quoted phrase like `description: Main heading, "Transfers: ready for takeoff"` breaks the parser — always fully quote a description value that itself contains a quoted phrase), confirm every cross-linked component slug resolves to a real file, and grep for banned dashes/vocabulary across everything before considering it done.
